# Рассылка по сделкам Битрикс24 с отбором получателей по фильтрам

Получатели не выбираются вручную. Вы задаёте условия (воронка, стадия, ответственный,
сумма, даты, любые поля сделки), инструмент сам находит **все** подходящие сделки
через API, берёт связанные контакты и их email, проверяет адреса и историю отправок,
показывает итог и **только после подтверждения** отправляет письма. Каждое письмо
привязывается к сделке и контакту и видно в их Timeline.

```
Сделка → связанный контакт → email → проверки → очередь → отправка → исходящее письмо в Timeline
```

## Быстрый старт

Нужен Python 3.11+, сторонние пакеты не требуются.

```bash
cp config.example.toml config.toml            # заполните [send].from
export BITRIX_WEBHOOK_URL="https://портал.bitrix24.ru/rest/1/xxxx/"

python -m bitrix_mailer fields                         # воронки, стадии, поля сделки
python -m bitrix_mailer preview campaigns/example.toml # предпросмотр, затем запрос «да»
python -m bitrix_mailer report 1                       # итоговый отчёт
```

Входящий вебхук создаётся в Битрикс24: *Разработчикам → Другое → Входящий вебхук*,
права: **CRM** и **Пользователи**.

## Фильтр

Задаётся в файле кампании (`campaigns/*.toml`) и/или в командной строке, в код не зашит:

```toml
[filter]
"Воронка" = "Холодная"
"Стадия" = "Свободные"
"Ответственный" = "Иван Иванов"
"Сумма" = "> 100000"
"Дата создания" = "последние 30 дней"
"Источник" = ["Звонок", "Веб-сайт"]   # любое из значений
"Регион" = "Москва"                    # пользовательское поле по названию…
"UF_CRM_1700000000" = "Да"             # …или по коду
```

```bash
python -m bitrix_mailer preview campaigns/example.toml -w "Сумма>100000" -w "Ответственный=Иван Иванов"
```

* Операторы: `=`, `!=`, `>`, `>=`, `<`, `<=`, `~` (содержит).
* Даты: `2026-09-01`, `01.09.2026`, `последние 30 дней`, `с 01.09.2026 по 30.09.2026`, `сегодня`.
* Названия воронок, стадий, пользователей и значений списков переводятся в ID через API.
  Если что-то не найдено — предпросмотр остановится с ошибкой и списком вариантов,
  а не отправит письма «не тем».
* Любое поле из `crm.deal.fields` можно указать по коду или подписи. Для особых случаев есть
  `[filter.raw]` — условия уходят в `crm.deal.list` как есть.
* Пустой фильтр запрещён (защита от рассылки по всей базе).

**Все страницы.** Сделки загружаются постранично до конца (быстрая пагинация по ID,
рекомендованная Битрикс24), контакты — пакетами `batch` по 50. Для 80 сделок будут
обработаны все 80, для 1000 — все 1000. Запросы идут не чаще 2 в секунду; при
`QUERY_LIMIT_EXCEEDED` клиент ждёт и повторяет. Число загруженных сделок сверяется с
`total` из API.

## Прочитано / не прочитано

`python -m bitrix_mailer report <id>` при каждом запуске спрашивает у Битрикс24, какие письма
открыли, и показывает «прочитано / не прочитано» со списками получателей; время открытия
попадает в колонку `read_at` CSV-отчёта. Битрикс24 ставит в письма из CRM пиксель
отслеживания и при открытии отмечает у дела «E-mail» `SETTINGS.READ_CONFIRMED` — инструмент
только читает это поле (`crm.activity.get`), в CRM ничего не меняет.

* Работает для `via = "bitrix"`. Письма через SMTP Битрикс24 не отслеживает.
* «Не прочитано» значит «нет отметки об открытии»: если у получателя отключены картинки
  (часто в Outlook и корпоративной почте), письмо может быть прочитано без отметки.
  Бывают и ложные «прочитано» — когда почтовый сервис сам загружает картинки (Apple Mail, Gmail).

## Несколько контактов в сделке

`contact_mode` в файле кампании или `--contact-mode`:

| значение | кому |
|---|---|
| `primary` (по умолчанию) | только основному контакту сделки (`IS_PRIMARY`, иначе первому по порядку) |
| `all` | всем связанным контактам; контакты без email попадают в отчёт как проблема |
| `valid_only` | всем связанным контактам с валидным email; остальные тихо исключаются |

Если один и тот же email встречается в нескольких сделках, письмо уходит один раз
(`dedupe_email = true`) — по первой сделке.

## Предпросмотр и подтверждение

```
Найдено по фильтру:     80 сделок
С контактами:           76
Без контакта:           4
С валидным email:       73
Без валидного email:    3
Уже получали письмо:    5
Будет отправлено:       68 писем по 68 сделкам

Причины исключения:
  – у сделки нет связанного контакта: 4
  – ...
Полный список получателей: reports/campaign-12.csv
```

`preview` сохраняет список в очередь и спрашивает «Отправить 68 писем? Введите «да»».
Можно отложить: `preview … --no-prompt`, затем `send 12` (снова покажет статистику и
спросит подтверждение) или `send 12 --yes`. Без подтверждения отправка невозможна.
Отправляется ровно тот список, который вы видели в предпросмотре.

`send 12 --dry-run` сохраняет все персонализированные письма в файлы, ничего не отправляя.

## История отправок

«Это письмо» определяется ключом `key` в файле кампании. Адрес, который уже получил письмо
с тем же ключом (в любой прошлой кампании), исключается. Проверка повторяется и прямо
перед отправкой каждого письма. Дополнительно можно искать прошлые письма в самом
Битрикс24 по части темы: `[history] bitrix_subject_contains = "…"`.

Если отправка прервалась, запустите `send <id>` ещё раз — продолжит с места остановки.
Письма, на которых процесс оборвался в момент отправки, помечаются «статус неизвестен» и
повторно не отправляются (чтобы не задублировать); `--retry-failed` повторяет письма с ошибкой.

## Привязка к CRM и Timeline

**`via = "bitrix"` (рекомендуется).** Письмо создаётся методом `crm.activity.add` как дело
«E-mail» (`TYPE_ID=4`, `DIRECTION=2` — исходящее) с владельцем — **сделкой** и получателем —
**существующим контактом** (`COMMUNICATIONS.ENTITY_ID`). Битрикс24 отправляет его из ящика,
подключённого к CRM (адрес в `[send].from`), и письмо видно как исходящее в Timeline сделки
и контакта. После создания инструмент читает дело обратно (`crm.activity.get`) и проверяет:
тип — письмо, направление — исходящее, владелец — нужная сделка, получатель — нужный контакт.
Результат проверки есть в отчёте и CSV (`timeline_verified`).

**`via = "smtp"`.** Письмо уходит через ваш SMTP; в Timeline сделки (и контакта) пишется
комментарий с темой, адресатом и текстом. Через вебхук нельзя создать «исходящее письмо»
без его отправки Битрикс24, поэтому это запасной вариант.

## Изменение сделок по вашей просьбе

Стадию, ответственного, сумму и другие поля **существующих** сделок можно менять — но
только отдельной командой и после подтверждения. Порядок тот же, что у рассылки:
план → «да» → изменение → журнал.

```bash
python -m bitrix_mailer update -w "Воронка=Холодная" -w "Стадия=Свободные" --set "Стадия=В работе"
python -m bitrix_mailer update --deals 12,15,40 --set "Ответственный=Пётр Петров"
python -m bitrix_mailer update --campaign campaigns/example.toml --set "Стадия=Отложено" --no-prompt
python -m bitrix_mailer update-apply 3      # применить план #3 (спросит «да» или --yes)
python -m bitrix_mailer update-undo 3       # вернуть старые значения
python -m bitrix_mailer updates             # журнал изменений
```

План показывает, сколько сделок найдено и что именно изменится
(«сделка #15: Стадия: Свободные → В работе»). Сделки, которые уже в нужном состоянии,
и сделки, в воронке которых нет такой стадии, пропускаются с объяснением. Для каждого
изменения сохраняются старые значения; откат не трогает поля, которые после нас успели
поменять вручную. Изменение стадии Битрикс24 сам показывает в Timeline сделки.

**Сменить стадию после рассылки** — секция в файле кампании:

```toml
[after_send]
"Стадия" = "Письмо отправлено"
```

Предпросмотр покажет, сколько сделок изменится. Изменение применяется только к сделкам,
по которым письмо действительно ушло, и попадает в тот же журнал (с откатом).

## Что инструмент не делает с CRM

Клиент API проверяет каждый вызов **до** отправки запроса. Разрешены: чтение;
`crm.activity.add` (только исходящее письмо, привязанное к существующей сделке/контакту,
получатель — существующий контакт с ID); `crm.timeline.comment.add` (только к
сделке/контакту); `crm.deal.update` — только у клиента, созданного командой изменения
сделок после вашего подтверждения, и только для существующей сделки по ID.

Запрещено в любом режиме:

* создавать и удалять лиды, сделки, контакты, компании;
* изменять контакты и компании;
* переносить сделку в другую воронку, менять её контакты, компанию и служебные поля;
* выполнять запись в пакетном `batch` (там только чтение).

Рассылка сама по себе сделки не меняет — только если вы задали `[after_send]`.
Получатель письма всегда передаётся с ID существующего контакта — Битрикс24 не будет
создавать новый контакт или лид по адресу.

## Структура

```
bitrix_mailer/
  client.py      REST-клиент, лимиты, пагинация, защита CRM
  filters.py     условия → фильтр crm.deal.list (названия → ID)
  recipients.py  сделки → контакты → email → проверки → очередь, статистика
  validation.py  проверка email (синтаксис, IDN, по желанию MX)
  template.py    персонализация: {{contact.NAME}}, {{deal.TITLE}}, {{deal.UF_CRM_…}}
  senders.py     отправка через Битрикс24 или SMTP, проверка Timeline
  updates.py     изменение полей сделок: план, применение, откат
  campaign.py    предпросмотр, очередь, отчёт
  storage.py     SQLite: кампании, получатели, история, журнал изменений сделок
campaigns/example.toml, templates/example.html, config.example.toml
tests/           тесты на имитации API Битрикс24: python3 -m unittest -v
```
